# Feature Roadmap Research — Comparable Local-First / Markdown Presentation Tools

**Purpose:** Primary-source survey of Marp (CLI + Core), Slidev, reveal.js, mdx-deck, and Deckset, to ground a prioritized "next ideal features" list for nh-deck against SOUL.md's four Non-Negotiables (local-first, no forced theme, no bundled Chromium, no silent scope expansion).

**Convention note:** This repo's only existing research artifacts live at `docs/research/*-research.md` (`security-performance-tooling-research.md`, `cli-robustness-testing-research.md`), not under `docs/adr/`. This file follows that established naming pattern rather than the `docs/adr/` nesting the delegating task suggested as a fallback.

**Methodology:** Every claim below is checked against a primary source — an official repo's README/docs markdown fetched directly from GitHub raw content, the tool's own source code, its docs site, or (for the one closed-source entry, Deckset) its own marketing/docs pages, explicitly flagged as such. Where a claim could be verified against actual package metadata (npm registry) rather than prose, that was done and is noted. All fetches performed 2026-09-10.

---

## 0. A foundational finding about nh-deck itself (context for everything below)

Before comparing to other tools: nh-deck's `src/render.ts:generateHtml()` currently calls `marked.parse(markdown, { async: false })` on the **entire file as one continuous document** and wraps the result in a single `<body>`. There is no `---`-based (or any other) per-slide segmentation — a Markdown `---` becomes a plain `<hr>` via `marked`'s default GFM behavior, not a slide boundary. `src/pdfExport.ts` then calls `page.pdf({ format: 'A4', printBackground: true })` against that same undivided HTML, with no `page-break` CSS rule anywhere — so PDF export produces a flowing multi-page document wherever content happens to overflow A4, not "one slide = one PDF page."

This matters because **every one of the five tools researched below treats `---`-delimited slide segmentation as foundational**, and most of the features nh-deck's own docs list as deferred (speaker notes, per-slide theming metadata, click-through navigation) depend on that segmentation existing first. This is reflected as Recommendation #1.

## 1. Live-reload / watch-mode preview

- **Marp CLI** ships `--watch`/`-w`: "Marp CLI will observe a change of Markdown and using theme CSS when passed with `--watch` (`-w`) option. The conversion will be triggered whenever the content of file is updated. While you are opening the converted HTML in browser, it would refresh the opened page automatically." It also has `--preview`/`-p`, which opens a dedicated preview window and auto-enables watch mode, and a `--server`/`-s` mode that serves a whole directory and **converts on-demand per HTTP request** rather than pre-rendering once, including format switching via query string (`http://localhost:8080/deck-a.md?pdf`). — `marp-team/marp-cli` README, "Watch mode" / "Server mode" / "Preview window" sections (`README.md`, fetched from `raw.githubusercontent.com/marp-team/marp-cli/main/README.md`).
- **Slidev** is a Vite dev server (Vue 3 SPA) — "⚡️ Fast — instant reloading powered by Vite." Live reload is full Vite HMR, not a lightweight file-watch-and-refresh; it comes with the cost of a real bundler/dev-server stack. — `slidevjs/slidev` README, "Features"/"Tech Stack" sections.
- **mdx-deck** similarly runs a webpack-based dev server ("Start the development server" via `mdx-deck deck.mdx`); no lighter-weight watch mode is documented. — `jxnblk/mdx-deck` `packages/mdx-deck/README.md`, "Getting Started".
- **reveal.js** is a framework, not a CLI with its own dev server; its README/docs don't document a built-in file-watcher at all — users typically pair it with an external static-file server. No live-reload claim exists in its primary docs.

**Takeaway for nh-deck:** nh-deck's own `AGENTS.md` currently *claims* the dev server supports "live reload," which `CODEBASE_INDEX.md` §8 already flags as false — `src/server.ts` has no watch/push mechanism at all. Marp CLI's model (fs-watch the input file + theme CSS, re-render, push a refresh to the open tab) is the right-sized reference: far lighter than Slidev's full Vite/Vue stack, and — critically — implementable as file-watch + a same-origin SSE endpoint served from the *existing* `127.0.0.1`-only `http.Server`, with an inline (not CDN) `<script>` for the `EventSource` client. That traffic never leaves loopback, so it is not a "runtime network dependency" in SOUL.md's sense.

## 2. Theming / templates as an opt-in, non-forced mechanism

- **Marp CLI/Marpit**: `--theme <name-or-path>` and `--theme-set <files-or-dir>` let a user pass a **custom CSS file** directly — "A custom theme created by user also can use easily by passing the path of CSS file... `marp --theme custom-theme.css`", and notably "it's not required" for the CSS file to declare the `@theme` metadata comment "in this usage" (CLI usage relaxes Marpit's normal theme-authoring requirement). Marpit also exposes a `style` **global directive** ("Specify CSS for tweaking theme") settable per-deck via YAML front-matter or an HTML comment, and a `theme` directive to pick a registered theme by name. — `marp-team/marp-cli` README "Theme" section; `marp-team/marpit` `docs/directives.md` "Global directives" table and "Theme"/"Tweak theme style" sections.
- **Slidev**: themes are npm packages ("🎨 Themable — theme can be shared and used with npm packages"), selected via frontmatter, with UnoCSS utility classes available inline for one-off styling. — `slidevjs/slidev` README "Features".
- **mdx-deck**: themes are plain JS objects (Theme UI spec) exported from the deck file (`export const theme = myTheme`), covering fonts/colors/layout/per-element `styles`; no CDN involved for the theme mechanism itself, though the theme spec includes a `googleFont` field that "automatically add[s] a `<link>` tag to the document head" if used — a CDN-injection footgun baked into the *theme* layer, not the core tool, worth avoiding if nh-deck ever grows a theme-object concept. — `jxnblk/mdx-deck` `docs/theming.md`.
- **Deckset** (closed-source; homepage/docs nav are the only available primary source, as instructed): "Choose from more than 25 built-in themes, or create your own with custom fonts, colors, and layouts." No markdown-level opt-out mechanism is documented (themes are chosen via the native macOS app, not a CLI flag). — `deckset.com` homepage copy, fetched via WebFetch.

**Takeaway for nh-deck:** Marpit's model is the closest fit to nh-deck's "no forced theme, opt-in only" Non-Negotiable: a **user-supplied CSS file path** (`--theme`/`--css` flag) plus an optional in-document `style:`-style directive, with *no default theme shipped that overrides the user's own styling*. This is exactly `CODEBASE_INDEX.md` §8's already-flagged tension ("`render.ts` unconditionally injecting a hardcoded `<style>` block... with no opt-out mechanism"), and Marpit's directive model is a concrete, low-risk way to add an opt-out without inventing a theme *system*.

## 3. Math (KaTeX) and diagram (Mermaid) rendering — dependency-size and network-access tradeoffs

This is the dimension with the sharpest findings, including two confirmed anti-patterns that nh-deck must **not** copy.

### 3a. KaTeX — CDN-by-default is the norm, and it's a real gotcha, not a hypothetical

- **reveal.js's own official KaTeX plugin defaults to loading from jsDelivr at runtime**, verified directly in its source: `plugin/math/katex.js` computes `let baseUrl = options.local || 'https://cdn.jsdelivr.net/npm/katex';` and then dynamically injects a `<link>` (CSS) and one-to-three `<script>` tags (KaTeX core, optional `mhchem` extension, `auto-render`) pointed at that CDN unless the deck author explicitly sets `katex: { local: 'node_modules/katex' }` in the Reveal config. The MathJax variant does the same thing for the JS bundle: `plugin/math/mathjax3.js` uses `let url = options.mathjax || 'https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-mml-chtml.js';`. Confirmed independently by revealjs.com/math/'s own docs: "by default the latest KaTeX is loaded from a remote server (https://cdn.jsdelivr.net/npm/katex)," with the same CDN-URL-as-default pattern repeated for all three MathJax major versions. (Sources: `hakimel/reveal.js` `plugin/math/katex.js` and `plugin/math/mathjax3.js`, fetched raw from GitHub; `revealjs.com/math/` docs page.)
- **Marp Core** has the identical shape of gotcha, just for *font files* rather than the whole library. In the current stable v4 line, the `math` constructor option's `katexFontPath` sub-option documents: "By default, Marp Core will use online web-font resources through jsDelivr CDN (`https://cdn.jsdelivr.net/npm/katex@latest/dist/fonts/`). You have to set path to fonts directory if you want to use local resources." In the v5 release-candidate line (where math moved to an optional `@marp-team/marp-core/plugins/katex` plugin, installed via `npm install katex` so the *JS/CSS* is a real local npm dependency, not a CDN script), the **font path default is still jsDelivr CDN** — "Default: Use KaTeX fonts through jsDelivr CDN (`https://cdn.jsdelivr.net/npm/katex/dist/fonts/`)" — unless the app explicitly sets `fontPath` when registering the plugin. (Sources: `marp-team/marp-core` `v4` branch `README.md` "`math` constructor option"; `main` branch `docs/configuration.md` "KaTeX" section.)
- **Slidev** bundles KaTeX as a real npm/Vite dependency via `markdown-it-katex` and renders LaTeX client-side inside its Vue SPA at view time — no CDN reference, but it requires a live JS runtime, which doesn't match nh-deck's single self-contained static-HTML-file architecture. (Source: `slidevjs/docs` `guide/syntax.md` "LaTeX" section.)
- **Deckset**: "Write TeX in Markdown. Deckset renders the formula as vector graphics." No rendering-engine or network-dependency detail is disclosed in the available primary sources (the detailed `08-formulas.html` doc page returned HTTP 403 to automated fetch). (Source: `deckset.com` homepage copy.)

**Implication for nh-deck:** if/when KaTeX ships, the correct design is to run KaTeX's Node-side `renderToString` API (browser-free, synchronous — fits `generateHtml`'s existing pure-function shape) and **embed the font files locally** (copied into the output alongside the HTML, or inlined as `data:` URIs) rather than defaulting `fontPath` to a CDN the way both Marp Core major lines do. This is precisely the scenario SOUL.md's CLAUDE.md gate exists for and its own Anti-Example #1 names directly ("Adding a KaTeX `<script src="https://cdn...">` tag ... just to unblock math rendering for now") — the fact that two of the five most popular tools in this space ship exactly that default is the concrete evidence that this default needs an explicit, deliberate override, not an accidental inheritance.

### 3b. Mermaid — build-time SVG rendering is the local-first-safe pattern; the popular CLI is not

- **Marp Core v5** (RC) renders Mermaid via a dedicated optional plugin backed by `beautiful-mermaid`: "Marp Core uses beautiful-mermaid for **deterministic server-side output**." That package's own README states "Ultra-fast, fully themeable, **zero DOM dependencies**... Pure TypeScript, works everywhere," and — verified directly against its published npm package metadata (`beautiful-mermaid@1.1.3`) — its only runtime dependencies are `elkjs` (a pure-JS graph-layout engine) and `entities` (HTML-entity encode/decode); no browser, no DOM, no Puppeteer. This is a genuinely local-first-compatible pattern: pure Node, no headless browser needed just to turn a `mermaid` code fence into an SVG. (Sources: `marp-team/marp-core` `main` `docs/markdown.md` "Mermaid diagrams"; `lukilabs/beautiful-mermaid` README; npm registry metadata for `beautiful-mermaid`, fetched 2026-09-10.)
- **By contrast, the popular official `@mermaid-js/mermaid-cli` package requires a real headless browser.** Verified directly against its published npm package metadata (`@mermaid-js/mermaid-cli@11.17.0`): it declares `puppeteer: "^23 || ^24 || ^25"` as a **required `peerDependency`** (no `peerDependenciesMeta.optional`), meaning a plain `npm install` will pull in the full `puppeteer` package — which bundles/downloads its own Chromium at install time. This is *exactly* the pattern SOUL.md's Anti-Example #3 warns about ("Silently swapping `puppeteer-core` for full `puppeteer`... without noticing it now bundles and downloads a Chromium binary at install time") and must be explicitly avoided as a dependency choice for nh-deck, even though it's the most commonly reached-for Mermaid CLI tool in the ecosystem. (Source: npm registry metadata for `@mermaid-js/mermaid-cli`, fetched 2026-09-10.)
- **Slidev** renders Mermaid client-side in the browser at view time via the real `mermaid` npm package bundled through Vite (README lists Mermaid directly in its "Tech Stack"); this works for Slidev's live-SPA model but, like its KaTeX approach, doesn't fit nh-deck's static-single-HTML-file output.
- **Deckset**: the existence of a documentation page at the URL slug `05-mermaid.html` under `docs.deckset.com`'s own navigation confirms Mermaid-based diagram support by name (the page body itself returned HTTP 403 to automated fetch, so only the URL/title is verifiable here, not the exact syntax or rendering mechanics).

**Implication for nh-deck:** a DOM-free, Puppeteer-free, build-time-to-SVG renderer (the `beautiful-mermaid` pattern, not the `mermaid-cli` pattern) is the only option that preserves `generateHtml`'s current browser-free, synchronous shape and doesn't quietly reintroduce a bundled-Chromium dependency through the back door of a diagram library.

## 4. Slide-splitting and frontmatter conventions

- **Marpit** (Marp's underlying framework) supports **both** a leading YAML front-matter block (`---\ntheme: default\npaginate: true\n---`) for global directives, **and** HTML-comment directives (`<!--\ntheme: default\n-->`) scoped either globally or per-slide (with a `_`-prefix for single-page-only "spot directives," e.g. `<!-- _backgroundColor: aqua -->`). Slides themselves are split on a `---` horizontal rule, same as nh-deck's own casual convention already implies. — `marp-team/marpit` `docs/directives.md` "Usage" and "Type of directives" sections.
- **Slidev**: slides split on `---`; each slide's own YAML frontmatter block (`layout: cover`, `background: ...`, `class: ...`) sets per-slide metadata, with a documented Prettier-compatibility escape hatch (a `yaml` code fence as the first block) for users whose formatters mangle the custom frontmatter syntax. — `slidevjs/docs` `guide/syntax.md` "Frontmatter & Layouts" / "Prettier Support".
- **reveal.js**: slides split on `---` for content typed directly in the page, or on a **regex-configurable separator** when loading an external Markdown file (`data-separator` defaulting to `^\r?\n---\r?\n$`, `data-separator-vertical` for nested/vertical slides, `data-separator-notes` for speaker-note boundaries). Per-slide/per-element metadata is **explicitly not** YAML frontmatter — it's HTML-comment pseudo-directives: `<!-- .slide: data-background="#ff0000" -->` for the whole slide, `<!-- .element: class="fragment" -->` for one element. — `revealjs.com/markdown/` docs page.
- **mdx-deck**: slides split on `---`; there is no frontmatter at all — per-deck theme/layout config is expressed as real JS (`export const theme = ...`, `import Layout from './Layout'`), which is idiomatic for an MDX+React tool but not portable to nh-deck's plain-Markdown model. — `jxnblk/mdx-deck` README "Getting Started"/"Layouts".
- **Deckset**: heading levels and lists drive slide/content structure directly ("Headings, paragraphs, and lists create slides with a consistent layout") rather than an explicit separator or frontmatter block, per its own homepage copy — the only primary source available for this closed-source product.

**Implication for nh-deck:** Marpit's dual model — a leading YAML front-matter block for deck-wide settings, plus scoped HTML-comment directives for per-slide overrides — is the best fit: it reuses the `---`-as-divider convention nh-deck's docs already assume, doesn't require inventing a new syntax, and (per §2 above) is also the natural home for an opt-in `--theme`/`style:` escape hatch.

## 5. Speaker notes

- **Marpit** collects **plain HTML comments** written in the slide Markdown (excluding any comment that parses as a directive) and returns them as a parallel, per-slide array from `marpit.render()`: "Marpit can collect HTML comments written in Markdown while rendering, except directives... The collected `comments` are returned in the result of `marpit.render()`... You may use it as the presenter notes." Marp CLI surfaces this directly as `--notes` (exports presenter notes to a `.txt` file) and `--pdf-notes` (embeds them as PDF page annotations). — `marp-team/marpit` `docs/usage.md` "Presenter notes"; `marp-team/marp-cli` README "Export presenter notes" section.
- **reveal.js**'s speaker-notes plugin opens a **second same-origin browser window** (`window.open('about:blank', 'reveal.js - Notes', ...)`) and synchronizes it with the main deck purely via `postMessage` — no server round-trip, no network call of any kind, verified directly in `plugin/notes/plugin.js`. — `hakimel/reveal.js` `plugin/notes/plugin.js`.
- **Slidev**: "the last comment block in each slide will be treated as a note," shown in its dedicated Presenter Mode (a `/presenter` route within its own dev server), with an optional `[click]` marker syntax to synchronize note-scrolling with click/fragment progress. — `slidevjs/docs` `guide/syntax.md` "Notes"; `guide/presenter-mode.md`.
- **mdx-deck**: a dedicated `<Notes>` MDX component wraps note content per slide, shown only in Presenter Mode (`Option+P`), which — like reveal.js — opens the deck in a second synchronized browser window/tab. — `jxnblk/mdx-deck` README "Presenter Mode"; `docs/presenting.md`.
- **Deckset**: "Keep context in presenter notes, preview the next slide, and rehearse with timing" — confirmed as a real, named feature ("Presenter Notes" appears in the docs site's own navigation), but the exact markdown syntax for authoring a note is undisclosed in the sources this research could reach (the dedicated docs page 403'd).

**Implication for nh-deck:** Marpit's comment-collection mechanism is the cleanest match for nh-deck's architecture — it requires **zero new syntax** (any HTML comment already passes through untouched today) and **zero new runtime dependency**, just a small change to `generateHtml` to also return a parallel notes structure once per-slide segmentation (Recommendation #1) exists. reveal.js's `window.open()` + `postMessage` pattern is the right model for *displaying* those notes during a live presentation without any server involvement, and is directly portable to nh-deck's existing loopback-only server.

## 6. Export formats beyond PDF

- **Marp CLI**: PPTX (including an experimental `--pptx-editable` mode requiring LibreOffice Impress on top of a browser), PNG/JPEG per-slide images, and plain HTML — all via the same browser-driven conversion path used for PDF (`chrome`/`edge`/`firefox`, auto-detected, with an explicit `--browser-path` override). — `marp-team/marp-cli` README "Convert to PowerPoint document"/"Convert to image(s)" sections.
- **Slidev**: `slidev export --format pdf|png|pptx|md`; PPTX/PNG/PDF export explicitly requires installing `playwright-chromium` as a separate dev dependency — i.e., Slidev's own documented export path is a full Playwright install that **does** trigger a bundled-browser download, the exact pattern nh-deck's Non-Negotiable #3 forbids. — `slidevjs/docs` `guide/exporting.md`.
- **mdx-deck**: a `build` script produces a static HTML+JS-bundle export; PDF and PNG are **not built in** at all — the docs point to third-party CLIs (`website-pdf`, `capture-website-cli`) that screenshot a running dev-server URL. — `jxnblk/mdx-deck` `docs/exporting.md`.
- **reveal.js**: no built-in export command. The documented, primary method is manual — open the deck with `?print-pdf` in the query string and use the browser's native "Save as PDF" print dialog (Chrome/Chromium only is "confirmed to work"), with config knobs like `pdfMaxPagesPerSlide` and `pdfSeparateFragments`. A command-line alternative, `decktape`, is mentioned by name only, with no further detail. — `revealjs.com/pdf-export/` docs page.
- **Deckset**: PDF only, per its own homepage copy — no PPTX, image, or video export is claimed anywhere in the available primary sources.

**Implication for nh-deck:** nh-deck's existing `pdfExport.ts` (puppeteer-core + chrome-launcher against a detected local browser, no bundled Chromium) is already the *most* local-first-compliant PDF export design of any tool surveyed here — Slidev's documented export path requires exactly the dependency nh-deck's SOUL.md forbids, and reveal.js doesn't automate export at all. This validates the current architecture rather than suggesting a change; the one genuine gap (per §0) is that it doesn't yet paginate one slide per PDF page. PPTX/PNG export is a plausible, lower-priority future extension using the same already-detected-browser pattern (`page.screenshot()` per slide section for PNG; PPTX would need a real library, unlike PDF/PNG which the existing browser can produce natively).

## Prioritized "Next Ideal Features for nh-deck"

Ordered by (foundational-ness × impact) ÷ effort. Every item includes an explicit Non-Negotiable compliance check.

### 1. Real per-slide segmentation (`---` → `<section>` boundaries)
**What:** Split the Markdown on `---` before calling `marked.parse()`, wrap each chunk in its own `<section>` (or similar), and add on-screen slide navigation (keyboard next/prev) plus print CSS to page-break between sections.
**Modeled on:** Marpit/Marp CLI's `---`-as-page-divider convention (`marp-team/marpit` docs), Slidev's identical `---` separator (`slidevjs/docs` `guide/syntax.md`), reveal.js's regex-configurable separator model (`revealjs.com/markdown/`), and mdx-deck's `---` divider (`jxnblk/mdx-deck` README).
**Effort/impact:** Medium effort, very high impact — every other deferred feature below (notes, per-slide PDF pagination, future click-throughs) depends on this existing first, and it closes the gap between what nh-deck's own example decks/docs already imply (`---` = new slide) and what the code actually does today (§0).
**Non-Negotiable check:** Fully compliant — pure string-splitting plus CSS/inline JS for navigation; no new dependency, no network surface.

### 2. Genuine live-reload for `render`
**What:** `fs.watch` the input Markdown (and any future theme CSS file), re-render on change, and push a refresh to the open tab via a same-origin SSE endpoint added to the existing `127.0.0.1`-only `http.Server`, with an inline (not CDN-hosted) `EventSource` client script.
**Modeled on:** Marp CLI's `--watch`/`--preview` (`marp-team/marp-cli` README) and its `--server` mode's on-demand-render-per-request pattern, which doubles as live-reload-on-manual-refresh for free.
**Effort/impact:** Low effort, high impact — this also *fixes an existing false claim*: `AGENTS.md`'s overview line already asserts "live reload" exists, which `CODEBASE_INDEX.md` §8 confirms is currently false.
**Non-Negotiable check:** Compliant as long as the SSE channel and its client script stay same-origin/inline over loopback — that is not a "runtime network dependency" in SOUL.md's sense (it never leaves the machine), but this is exactly the kind of change CLAUDE.md's stop-and-ask gate should confirm before implementation, given how easily a "just add a small reload script" edit could accidentally reach for a CDN-hosted livereload library instead of hand-rolling ~20 lines.

### 3. Presenter notes via plain-HTML-comment convention
**What:** Extend `generateHtml` to also return a parallel per-slide notes array, collected from HTML comments in each slide's Markdown (excluding any comment later used for a directive, if item 4 below ships), surfaced as a simple `?notes` view or companion pane served from the same local server.
**Modeled on:** Marpit's comment-collection mechanism, returned as a two-dimensional array from `marpit.render()` (`marp-team/marpit` `docs/usage.md`), and Slidev's "last comment block is a note" convention (`slidevjs/docs` `guide/syntax.md`). Displaying them live, if desired, should follow reveal.js's `window.open()` + `postMessage` pattern (`hakimel/reveal.js` `plugin/notes/plugin.js`) rather than anything server-mediated.
**Effort/impact:** Low-medium effort (depends on #1 for slide boundaries), medium-high impact — a commonly expected feature for any tool calling itself a "slide deck" tool.
**Non-Negotiable check:** Fully compliant — zero new dependency, zero network, reuses syntax (`<!-- ... -->`) that already passes through untouched today.

### 4. Per-slide PDF pagination
**What:** Once slides are real `<section>` elements (#1), add `@media print { section { page-break-after: always } }` (or the modern `break-after` equivalent) so `pdfExport.ts`'s existing `page.pdf()` call produces one PDF page per slide instead of a flowing document.
**Modeled on:** the pagination behavior every surveyed tool treats as a baseline (Marp CLI's PDF output, reveal.js's `pdfMaxPagesPerSlide`/`pdfSeparateFragments` config per `revealjs.com/pdf-export/`).
**Effort/impact:** Low effort once #1 lands (a CSS rule, no new dependency), high impact — closes a real gap against SOUL.md's own Mission statement ("export it to a PDF that looks like what was on screen").
**Non-Negotiable check:** Fully compliant.

### 5. Opt-in, locally-bundled KaTeX math support
**What:** Add math rendering using KaTeX's Node-side `renderToString` (synchronous, browser-free — fits `generateHtml`'s current shape), with font files copied/embedded locally rather than fetched from any CDN, gated behind explicit user opt-in per CLAUDE.md's stop-and-ask process.
**Modeled on:** Marp Core's plugin architecture for *choosing to add* math support (`marp-team/marp-core` `docs/markdown.md`) — but deliberately **inverting** its font-path default, which is CDN in both its stable v4 and RC v5 lines (`v4` README's `katexFontPath` option; `main` `docs/configuration.md`'s `fontPath` option, both defaulting to `cdn.jsdelivr.net/npm/katex`) — and explicitly avoiding reveal.js's official KaTeX/MathJax plugins' pattern of injecting `<script>`/`<link>` tags pointed at jsDelivr **by default**, confirmed directly in their source (`hakimel/reveal.js` `plugin/math/katex.js`, `plugin/math/mathjax3.js`).
**Effort/impact:** Medium effort (font packaging/embedding is the fiddly part), high impact — this is Context.md's longest-standing deferred item.
**Non-Negotiable check:** This is the one feature genuinely **in tension** with Non-Negotiable #1 unless built carefully — two of the five researched tools default to exactly the CDN pattern SOUL.md's Anti-Example #1 forbids. The correct implementation bundles fonts locally with no CDN fallback path at all (not even as an "advanced" opt-in), and must go through the explicit stop-and-ask gate in `CLAUDE.md` before any code lands.

### 6. Opt-in, build-time Mermaid diagram support
**What:** Render `mermaid` code fences to static SVG at render time using a DOM-free, browser-free library, gated behind the same explicit-opt-in gate as math.
**Modeled on:** Marp Core v5's `beautiful-mermaid`-backed plugin, described in its own docs as "deterministic server-side output" (`marp-team/marp-core` `docs/markdown.md`), and verified via `beautiful-mermaid`'s own README claim of "zero DOM dependencies" plus its actual npm package metadata (`elkjs` + `entities` only, no browser, no Puppeteer, confirmed via the npm registry).
**Effort/impact:** Medium effort, high impact, pairs naturally with #5.
**Non-Negotiable check:** Compliant **only if a DOM-free renderer is chosen** — the most popular Mermaid CLI tool in the ecosystem, `@mermaid-js/mermaid-cli`, is explicitly **not** safe to reach for here: its published npm metadata declares a required (non-optional) `peerDependency` on full `puppeteer@^23||^24||^25`, which bundles/downloads its own Chromium — exactly the trap SOUL.md's Anti-Example #3 names. This must be called out explicitly if this feature is ever scoped, since it's the "obvious" package name a search would surface first.

### 7. `--theme`/`--css` opt-out flag for the baseline stylesheet
**What:** Let a user pass a custom CSS file (or a `style:`/`theme:`-style front-matter directive) that fully or partially overrides `render.ts`'s currently hardcoded, no-opt-out `<style>` block.
**Modeled on:** Marp CLI's `--theme <path-to-css>` (which explicitly relaxes Marpit's normal theme-metadata requirement for this exact CLI-usage case) and Marpit's `style` global directive (`marp-team/marpit` `docs/directives.md`).
